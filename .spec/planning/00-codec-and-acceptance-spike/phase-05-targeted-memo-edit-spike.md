# Phase 5: Targeted Memo Edit Spike

**Description:** Prove that one existing property or named method can be changed
through a pure, hash-bound edit plan whose semantic result and exact byte
footprint are verifiable on generated bytes and disposable fixture copies.

**Status:** Planned

**Dependencies:** Phase 2 physical codec, Phase 3 semantic model, and the admitted
native fixtures from Phase 4.

## Section 5.1 — Property Edit Planning

**Description:** Plan narrowly scoped changes to supported property assignments
without altering sibling properties, formatting, or unrelated memo content.

### Task 5.1.1 — Resolve and Guard the Property Target

**Description:** Identify exactly one object and property from canonical semantic
identity and reject ambiguous or stale requests.

#### Subtask 5.1.1.1 — Resolve the Object Path

**Description:** Use the shared canonical path parser and document index, not
`OBJNAME` alone or physical record order.

- [ ] Missing, malformed, and ambiguous paths return stable findings and no plan.

#### Subtask 5.1.1.2 — Verify the Expected Old Value

**Description:** Require a typed or exact-verbatim precondition appropriate to
the requested property change before rendering any replacement bytes.

- [ ] Duplicate properties or a mismatched precondition return no memo append or DBF patch.

- [ ] Task 5.1.1 is complete with success, missing, duplicate, and stale-value cases.

### Task 5.1.2 — Render the Property Replacement

**Description:** Encode a supported typed value in the source code page and
replace only the selected assignment span.

#### Subtask 5.1.2.1 — Render Supported Literal Types

**Description:** Support strings, booleans, integers, decimals, `.NULL.`, and the
explicitly tagged date/datetime forms accepted by the property codec.

- [ ] Rendering preserves the target's name spelling, separators, surrounding whitespace, and line-ending convention where safe.

#### Subtask 5.1.2.2 — Reject Unsafe Rendering

**Description:** Reject unsupported expressions, malformed target lines,
unrepresentable characters, implicit code-page changes, and value overflow.

- [ ] Failed rendering returns findings only and leaves all source bytes untouched.

- [ ] Task 5.1.2 is complete with byte-span assertions for every supported literal type.

### Task 5.1.3 — Produce the Property `EditPlan`

**Description:** Convert the replacement memo payload into explicit FPT append
operations and DBF pointer patches bound to the exact source snapshot.

#### Subtask 5.1.3.1 — Plan the Memo Append

**Description:** Retain the replaced block type, align at the effective block
size, update next-free metadata consistently, and leave the old block unreachable
rather than overwriting it.

- [ ] The plan lists every appended and header byte range with before/after expectations.

#### Subtask 5.1.3.2 — Plan the DBF Pointer Patch

**Description:** Patch only the selected record's property-memo pointer and any
explicitly accepted metadata bytes; preserve timestamp bytes during the spike.

- [ ] The expected footprint excludes every unrelated record, field, and memo allocation.

- [ ] Task 5.1.3 is complete when `VfpMcp.Edit.Properties.plan/4` returns a deterministic plan or findings.

## Section 5.2 — Named Method Edit Planning

**Description:** Plan replacement of exactly one named method block while
preserving sibling code and invalidating the affected compiled `OBJCODE`.

### Task 5.2.1 — Resolve and Guard the Method Target

**Description:** Identify one object and one unambiguous named method using the
semantic path and method index.

#### Subtask 5.2.1.1 — Resolve the Named Block

**Description:** Apply the defined method-name comparison policy and reject
missing, duplicate, overlapping, or malformed blocks.

- [ ] Marker text inside strings or comments cannot redirect the target span.

#### Subtask 5.2.1.2 — Verify Source Preconditions

**Description:** Require the expected old body/hash or an exact expected literal
match count before creating replacement content.

- [ ] Stale bodies and unexpected match counts fail without producing physical operations.

- [ ] Task 5.2.1 is complete with named-replace and exact-count patch cases.

### Task 5.2.2 — Render the Method Replacement

**Description:** Replace only the chosen procedure body or guarded literal span
while preserving declaration, terminator, siblings, comments, and line endings.

#### Subtask 5.2.2.1 — Render Named-Body Replacement

**Description:** Encode the requested source strictly and retain the surrounding
method bookends unless the documented operation explicitly replaces them.

- [ ] The rendered memo differs only inside the selected method span.

#### Subtask 5.2.2.2 — Render Guarded Literal Patch

**Description:** Apply replacement only when the exact source literal occurs the
declared number of times within the selected method block.

- [ ] Zero or excess matches fail without editing a sibling or another object.

- [ ] Task 5.2.2 is complete with mixed-case, extended-character, and multi-method tests.

### Task 5.2.3 — Produce the Method `EditPlan`

**Description:** Plan the methods-memo append, pointer update, and `OBJCODE`
invalidation as one pure, reviewable result.

#### Subtask 5.2.3.1 — Plan Memo and Pointer Changes

**Description:** Use the same aligned append and source-hash binding contract as
property edits while preserving the original methods block type.

- [ ] All memo and pointer changes appear explicitly in the expected footprint.

#### Subtask 5.2.3.2 — Plan `OBJCODE` Invalidation

**Description:** Clear only the affected record's `OBJCODE` memo pointer and do
not infer or generate compiled code.

- [ ] The plan verifies the original `OBJCODE` field bytes before applying its zero pointer.

- [ ] Task 5.2.3 is complete when `VfpMcp.Edit.Methods.plan/5` returns a deterministic plan or findings.

## Section 5.3 — Pure Materialization and Footprint Verification

**Description:** Apply an accepted `EditPlan` to in-memory bytes, then verify its
declared physical and semantic postconditions without writing production files.

### Task 5.3.1 — Materialize DBF and FPT Results Purely

**Description:** Produce a new pair snapshot from the source snapshot and plan,
using checked non-overlapping patches and appends.

#### Subtask 5.3.1.1 — Validate Plan Identity and Preconditions

**Description:** Recompute member and pair hashes and verify every expected-before
range before applying any operation.

- [ ] A stale hash, unexpected byte, overlapping patch, or out-of-bounds range rejects the whole materialization.

#### Subtask 5.3.1.2 — Apply Operations Atomically in Memory

**Description:** Build both result byte strings without mutating caller-owned
buffers or exposing a partially materialized pair.

- [ ] Failure yields no result snapshot and successful materialization is deterministic.

- [ ] Task 5.3.1 is complete with same-size, growing, and shrinking semantic replacements.

### Task 5.3.2 — Verify the Exact Physical Footprint

**Description:** Compare source and result snapshots and reconcile every changed
byte with the plan's declared patches, appends, and permitted alignment padding.

#### Subtask 5.3.2.1 — Compute Byte-Range Differences

**Description:** Produce deterministic changed ranges for both pair members and
classify each range by planned operation.

- [ ] Any changed byte outside the declared footprint fails verification.

#### Subtask 5.3.2.2 — Verify Unchanged Content

**Description:** Explicitly compare unrelated records, fields, properties,
methods, deleted records, opaque memos, padding, and record order.

- [ ] All unrelated bytes remain identical even when the replacement changes memo allocation length.

- [ ] Task 5.3.2 is complete across block sizes 1, 64, and 512.

### Task 5.3.3 — Verify Semantic Postconditions

**Description:** Reparse the result through the independent parse boundary and
confirm the requested semantic change and mutation eligibility.

#### Subtask 5.3.3.1 — Verify the Target Change

**Description:** Confirm the exact new property value or method body at the same
canonical object path and require no new fatal finding.

- [ ] The result demonstrates the declared semantic postcondition.

#### Subtask 5.3.3.2 — Verify Sibling Preservation

**Description:** Compare all unrelated semantic values, method hashes, hierarchy,
record identities, and expected findings between source and result.

- [ ] Self-reparse is recorded as automated evidence but is not labeled native acceptance.

- [ ] Task 5.3.3 is complete with postcondition and sibling-preservation proof.

## Section 5.4 — Phase 5 Integration Tests

**Description:** Exercise property and method plans end to end on generated pairs
and disposable copies of every applicable admitted native fixture.

### Task 5.4.1 — Run the Property Edit Matrix

**Description:** Plan, materialize, diff, and reparse supported property changes
across values, source sizes, encodings, pair versions, and FPT block sizes.

#### Subtask 5.4.1.1 — Test Successful Changes

**Description:** Cover same-size, growing, and shrinking replacements for each
supported literal type with siblings, formatting, and opaque content present.

- [ ] Every result satisfies its semantic postcondition and exact byte footprint.

#### Subtask 5.4.1.2 — Test Rejections

**Description:** Cover missing paths, duplicates, stale values and hashes,
unsupported expressions, lossy encoding, limits, and malformed memos.

- [ ] Every rejected request produces no result bytes or partial plan.

- [ ] Task 5.4.1 is complete for generated, VFP6, and VFP9 fixture cases.

### Task 5.4.2 — Run the Method Edit Matrix

**Description:** Plan, materialize, diff, and reparse named-body replacements and
guarded literal patches with multiple sibling methods and compiled `OBJCODE`.

#### Subtask 5.4.2.1 — Test Successful Changes

**Description:** Cover same-size, growing, and shrinking method changes and exact
one-match patches under supported encoding and block-size variants.

- [ ] Target source changes, sibling source stays byte-identical, and `OBJCODE` is cleared only for the affected record.

#### Subtask 5.4.2.2 — Test Rejections

**Description:** Cover ambiguous methods, malformed bookends, stale source,
incorrect match count, unencodable text, and plan tampering.

- [ ] Every rejected request preserves source snapshots exactly.

- [ ] Task 5.4.2 is complete for generated, VFP6, and VFP9 fixture cases.

### Task 5.4.3 — Verify the Milestone Boundary

**Description:** Confirm the spike remains a pure library experiment and has not
introduced production write or protocol capabilities.

#### Subtask 5.4.3.1 — Exercise Disposable-Copy Handling

**Description:** When a test uses filesystem copies, create them under the test
temporary directory, materialize results from memory, and remove only that
validated temporary location.

- [ ] No test writes to committed fixtures, raw intake, or original application trees.

#### Subtask 5.4.3.2 — Assert Deferred Components Remain Absent

**Description:** Confirm no writer process, lock, backup, journal, pair commit,
MCP write tool, or structural editor is required or exposed.

- [ ] The spike can run entirely through pure API calls under `mix test`.

- [ ] Task 5.4.3 is complete with the scope-boundary assertion passing.

## Phase 5 Completion Evidence

**Description:** Record proof only after every Phase 5 task and integration test
is complete.

- [ ] Property and method planner APIs and typespecs are linked.
- [ ] Successful and rejection matrices pass for generated and native fixtures.
- [ ] Exact byte-footprint and opaque-content comparisons pass.
- [ ] Semantic postcondition and `OBJCODE` invalidation checks pass.
- [ ] Tests prove that only disposable copies or in-memory bytes are changed.
- [ ] Phase status and the stream index are updated only after all evidence is linked.
